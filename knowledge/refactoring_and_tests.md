# リファクタリングとテストの教訓

## 背景

`renderFrame` / `renderTextFrame` / `renderRevolveFrame` の3関数を、`EffectModel.DrawContent` クロージャによる統合 `renderFrame` 1関数にリファクタリングした際に学んだこと。

---

## 教訓1: 設計変更はテストに先に反映する

**何が起きたか:**  
実装を先に変更し、テストは後から「コンパイルが通る最低限」にとどめてしまった。  
`IsRevolve bool` / `Lines []string` / `Chars []string` / `OrbitRadius float64` などの検証が消え、`DrawContent != nil` という trivially true なチェックだけが残った。

**ルール:**  
> 設計の変更（インターフェース・型・フィールド構造の変化）が決まったら、実装に手をつける前にテストを新しい設計に合わせて書き直す。

- テストを先に壊す → 実装を変えて通す、という順序がリファクタリングの基本
- テストが先に壊れていれば「どの検証が消えたか」が明確になる

---

## 教訓2: 実装の詳細ではなく振る舞いをテストする

**変更前の問題のあったテスト:**
```go
if !m.IsRevolve { t.Error(...) }
if len(m.Chars) != len(want) { ... }
if m.OrbitRadius <= 0 { ... }
```
これらは `EffectModel` の内部フィールドを直接チェックしており、実装詳細に依存していた。

**改善後:**
```go
img0 := renderFrame(m)
if !hasNonBgPixels(img0, white) { t.Error("文字が描画されていない") }
img2 := renderFrame(effect2(2, 8))
if imagesEqual(img0, img2) { t.Error("アニメーションが進んでいない") }
```
実際の出力（画像）を通じて振る舞いを検証している。

**ルール:**  
> 内部フィールドや中間データ構造が変わっても、「何を描画するか」という振る舞いは変わらない。テストは後者に対して書く。

---

## 教訓3: カプセル化が進むとテストの入口を変える必要がある

**今回の変化:**  
`EffectModel` に `Lines`, `Chars`, `OrbitRadius` が公開フィールドとして存在 → `DrawContent` クロージャ内にキャプチャされ外から見えなくなった。

このとき「フィールドが消えたからテストが書けない」ではなく、**公開されている別の入口（`renderFrame` の出力）を使う**。

**テストの入口の優先順位:**
1. 最終出力（`renderFrame` が返す `image.Image`）— 最も安定
2. 中間 DTO のフィールド（`EffectModel.Params` の数値）— 計算ロジックの単体テストに有効
3. 内部フィールド（`Lines`, `Chars` 等）— 実装詳細。変わりやすいので最終手段

---

## チェックリスト（リファクタリング時）

- [ ] 変更前に既存テストが何を検証しているかを把握する
- [ ] 設計変更で「消える検証」を洗い出す
- [ ] 消える検証を新しい設計で等価な振る舞いテストに書き直す（実装前）
- [ ] 実装後にテストが通ることを確認する
- [ ] integration test でビジュアル回帰がないことを確認する
